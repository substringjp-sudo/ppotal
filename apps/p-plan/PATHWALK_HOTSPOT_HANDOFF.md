# PATHWALK 체류 탐지 이관 명세 — 누적 브러시 방식

PATHWALK의 `SessionFootprintBuilder`(원반 합집합 → 마칭 스퀘어)를 대체하는 체류 탐지
알고리즘의 명세다. 참조 구현이 이 레포에 TypeScript로 있고, PATHWALK는 이걸 Kotlin으로
옮긴다.

**참조 구현**: `apps/p-plan/packages/shared/src/lib/trajectory-hotspots.ts`
(순수 함수 — 네트워크·지도 API·플랫폼 API를 쓰지 않는다. 전부 기기 안에서 돈다.)

**검증 하네스**: `apps/p-plan/packages/shared/src/lib/test-trajectory-hotspots.ts`
아래 §7의 합성 궤적을 그대로 만들어 돌린다. `apps/p-plan`에서:

```
npx -y tsx@latest packages/shared/src/lib/test-trajectory-hotspots.ts
```

## 1. 무엇을 하는가

지나간 길을 "가운데는 진하고 멀어질수록 연해지는 반투명 붓"으로 칠한다. 스쳐 지나간
길은 얇게 한 번 칠해지지만, 한자리에 머물거나 근처를 배회하면 같은 칸이 반복해서 칠해져
진해진다. 진하게 칠해진 영역이 "머문 곳"이다.

기존 반경·시간 임계값 방식으로 못 푸는 것:

- 큰 공원 안에서 300m 걸어다닌 것 ↔ 300m 떨어진 다른 가게로 이동한 것 — 거리로는 못 가른다
- 한자리에 오래 머물면 반경이 좁고, 배회하면 넓다 — 하나의 반경으로 둘 다 못 잡는다

"얼마나 멀리 갔나"가 아니라 "어디에 시간이 쌓였나"를 보므로 둘 다 자연히 풀린다.

## 2. 파이프라인 어디에 들어가는가

```
GpsSanitizer → KalmanFilter → PathCleaner
     → MotionClassifier → (페리 검사) → TransitModeMatcher
          → 맵매칭
               → [여기] 누적 브러시 체류 탐지     ← SessionFootprintBuilder 대체
                    → PathwalkTracePoint 로 pplan 전송
```

앞단은 **손대지 않는다.** 정제·수단 확정·맵매칭은 이미 잘 돌고 있고, 이 알고리즘은 그
결과(정제된 좌표 + 이미 판정된 이동 상태)를 입력으로 받는다. 특히 `MotionClassifier`가
프레임마다 계산해 둔 값을 **붓의 진하기로 재사용**하므로 새 센서 로직이 필요 없다.

## 3. 포팅하며 반드시 지켜야 할 두 가지

이 둘이 알고리즘의 핵심이다. 최적화하다 깨뜨리기 쉬우니 주석으로 남겨 둘 것.

### 3-1. 붓이 칠하는 것은 표본 개수가 아니라 **경과 시간**이다

GPS 표본 간격은 기기·배터리 상태에 따라 들쭉날쭉하다. 표본 개수로 세면 고주파로 쏟아진
구간이 오래 머문 것처럼 보인다. 표본이 아니라 **표본 사이 구간의 경과 시간**을 칠하므로
표본이 100개든 3개든 10분은 10분으로 칠해진다.

### 3-2. 임계값은 영역을 오려내는 데만 쓰고, 판정은 영역에 쌓인 **총량**으로 한다

봉우리 높이로 판정하면 한자리에 선 사람만 걸리고 넓게 배회한 사람은 놓친다 — 같은 시간을
넓게 퍼뜨리면 봉우리가 낮아지기 때문이다. 총량은 퍼짐과 무관하게 보존되므로 둘 다 잡힌다.

## 4. 알고리즘

### 4-0. 입력

| 필드 | 필수 | 설명 |
|---|---|---|
| `timestamp` | ✓ | ISO 또는 epoch millis |
| `lat`, `lng` | ✓ | 정제를 마친 좌표 |
| `accuracy` | 권장 | GPS 오차 반경(m). 붓 굵기를 정한다 |
| `speed` | 선택 | m/s |
| `motion` | 권장 | 이미 판정된 이동 상태 |

시간순 정렬하고, `accuracy > maxAccuracyMeters`인 표본은 버린다. 2개 미만이면 빈 결과.

### 4-1. 평면 투영

기준점(첫 표본) 주변을 등거리 원통 근사로 편다. 도시 하나 규모에서 오차는 무시할 수준이고,
격자 계산을 전부 미터 단위로 할 수 있어 훨씬 단순해진다.

```
mPerDegLat = 111320
mPerDegLng = 111320 · cos(refLat)
x = (lng − refLng) · mPerDegLng
y = (lat − refLat) · mPerDegLat
```

### 4-2. 붓질 — 연속한 표본 쌍마다

```
dt = t[i+1] − t[i]
dt ≤ 0  또는  dt > maxGapMinutes  →  건너뛴다 (끊긴 구간은 잇지 않는다)
dist = hypot(dx, dy)
dist / dt > 80 m/s  →  건너뛴다 (GPS 튐)

# 속도 판정 — 4-3 참조. 오차를 뺀 유효 변위로 판정한다
noiseFloor  = (σ[i] + σ[i+1]) / 2
impliedSpeed = max(0, dist − noiseFloor) / dt

w = min( sampleWeight(i, impliedSpeed), sampleWeight(i+1, impliedSpeed) )

# 표본이 성겨도 그 사이를 지나간 건 사실이므로 선을 따라 나눠 칠한다.
# 이렇게 해야 표본 간격이 벌어진 이동 구간이 "뚝뚝 떨어진 체류"로 보이지 않는다.
steps = clamp(ceil(dist / cellMeters), 1, 400)
각 step k:
    f  = (k + 0.5) / steps
    px = x[i] + dx·f,  py = y[i] + dy·f
    σ  = lerp(σ[i], σ[i+1], f)
    paintGaussian(px, py, mass = dt·w/steps, σ)

# 시간 지분은 양 끝 표본이 절반씩 나눠 갖는다 (나중에 방문별 체류량 계산에 쓴다)
shareSec[i]   += dt·w/2
shareSec[i+1] += dt·w/2
```

**`paintGaussian(px, py, mass, σ)`** — 격자 위에서 **이산 정규화**하는 게 중요하다:

```
radius = max(cellMeters, 2σ)
radius 안의 각 칸에 대해:
    d² = (칸 중심 − (px,py))²
    d² > radius² 이면 건너뜀
    k  = exp(−d² / 2σ²)
    수집하고 sum += k
각 칸: grid[칸] += mass · k / sum        ← sum으로 나누는 것이 이산 정규화
```

이렇게 해야 **붓이 굵어져도(GPS가 부정확해도) 총량이 보존되고 봉우리만 낮아진다.**
즉 부정확한 표본은 저절로 약한 증거가 된다. 연속 가우시안 공식(`1/(2πσ²)`)을 그대로
쓰면 격자가 σ에 비해 성길 때 총량이 안 맞는다.

### 4-3. 이동 상태 → 붓 진하기

```
stationary 1.0 │ walking 0.85 │ running 0.4 │ cycling 0.25 │ vehicle 0.05 │ unknown 0.85
```

속도로부터 (태그가 없을 때):

```
< 0.5 m/s → 1.0   < 2.0 → 0.85   < 4.0 → 0.4   < 8.0 → 0.25   그 외 → 0.05
```

**표본 하나의 가중치** = `min(태그값 ?? implied, 자체속도값 ?? implied, implied)`
— 태그를 믿되 실제 변위로 한 번 더 검증한다. 60초에 500m를 갔다면 태그가 뭐라고 하든
서 있던 게 아니다.

> **걷기를 크게 깎지 않는 것이 중요하다.** 넓은 장소 안을 돌아다니는 것도 엄연한 체류다.
> "통과"와 "배회"는 이 가중치가 아니라 **격자 누적이 알아서 가른다** — 통과는 선으로 얇게
> 흩어지고, 배회는 같은 동네에 반복해서 쌓인다. 반면 차량은 신호 대기로 멈춰 서도 방문이
> 아니므로 확실히 죽인다.

**PATHWALK 이동 수단 매핑** (PATHWALK가 pplan보다 분류가 세분화되어 있다):

| PATHWALK | 가중치 |
|---|---|
| `WALK` | 0.85 |
| `BICYCLE` | 0.25 |
| `VEHICLE` / `BUS` / `SUBWAY` / `TRAIN` / `FERRY` | 0.05 |

> `SUBWAY`/`TRAIN`은 지하 구간에서 GPS가 튀거나 정확도가 급락한다. `maxAccuracyMeters`
> 필터와 80 m/s 튐 가드가 1차 방어선이지만, PATHWALK는 이미 `TransitModeMatcher`로
> 노선을 확정하므로 그 구간은 태그만으로도 확실히 죽는다.

### 4-4. 임계값 — "그냥 걸어 지나갔을 때"의 몇 배인가

속도 v로 지나가면 한 칸에 쌓이는 양은 아래로 수렴한다(경로에 수직인 가우시안을 경로
방향으로 적분한 값):

```
walkThroughPerCell = cellMeters² / (1.4 · refSigma · √(2π))
thresholdSec       = walkThroughPerCell · separationFactor
```

`refSigma`는 전체 표본 σ의 **중앙값**. 이 기준선을 쓰면 격자 크기나 GPS 품질이 달라져도
임계값이 함께 움직여 손댈 필요가 없다.

> 분자에 가중치를 곱하지 않는다(= 최대치 1로 본다). 표본이 촘촘하면 걷는 중에도 변위가
> 오차 이하라 정지로 분류돼 만점 가중치로 칠해지기 때문이다. **최악의 경우를 기준선으로
> 삼아야 통과 구간이 임계값을 넘지 않는다.** (§6-2 참조)

### 4-5. 영역 만들기

`thresholdSec` 이상인 칸만 남기고, **4-이웃 연결 요소**로 묶는다(flood fill).
영역마다: 소속 칸 목록, 총량(`mass` = 칸 값의 합), 봉우리(`peak` = 최대 칸 값).

중심은 **농도 가중 중심**, 반경은 면적을 원으로 환산:

```
center = Σ(칸중심 · 칸값) / Σ칸값
radius = √(칸수 · cellMeters² / π)
```

### 4-6. 같은 영역이라도 다시 찾아왔으면 다른 방문이다

격자는 오전에 들른 것과 저녁에 다시 들른 것을 한 덩어리로 합쳐 놓는다. 표본을 각자 속한
영역에 배정한 뒤, **시간순으로 훑어 공백이 `revisitGapMinutes`를 넘으면 끊는다.**
공간은 같지만 시간이 다른 방문으로 나뉜다.

각 방문의 체류량 = 그 방문에 속한 표본들의 `shareSec` 합. (격자 총량이 아니라 표본 지분을
쓰는 이유: 격자는 여러 방문이 합쳐져 있어 방문별로 나눌 수 없다.)

`dwellMinutes < minDwellMinutes`인 방문은 버린다.

### 4-7. 확신도

```
dwellScore    = dwell / (dwell + minDwellMinutes)          # minDwell에서 0.5, 길수록 →1
concentration = clamp(peak / (threshold · 4), 0, 1)         # 좁은 데 진하게 뭉쳤나
fixQuality    = clamp(1 − (medianσ − minσ)/(maxσ − minσ), 0, 1)

confidence = 0.5·dwellScore + 0.3·concentration + 0.2·fixQuality
```

## 5. 매개변수

| 이름 | 기본값 | 의미 |
|---|---|---|
| `cellMeters` | 10 | 격자 한 칸 |
| `minDwellMinutes` | 8 | 이만큼 쌓여야 체류로 인정 |
| `maxGapMinutes` | 20 | 이보다 긴 공백은 궤적을 끊는다 |
| `revisitGapMinutes` | 30 | 이만큼 자리를 비웠다 돌아오면 다른 방문 |
| `minAccuracyMeters` | 12 | 붓 최소 굵기 (GPS가 더 정확하다 해도 이보다 좁게 안 칠함) |
| `maxAccuracyMeters` | 100 | 이보다 부정확한 표본은 버림 |
| `separationFactor` | 3 | 통과 대비 몇 배를 임계값으로 |

## 6. 포팅 중 재발시키면 안 되는 결함 두 개

참조 구현을 검증하다 발견해 고친 것들이다. 둘 다 겉보기엔 멀쩡히 돌아가서 눈으로는
못 잡는다.

### 6-1. GPS 지터를 이동으로 오인 (§4-2의 `noiseFloor`)

가만히 서 있어도 좌표는 오차 반경 안에서 계속 흔들린다. 표본 간격이 촘촘할수록 그 흔들림이
큰 속도로 환산돼(5초에 9m = 1.8 m/s) **서 있는 사람이 걷거나 뛰는 걸로 잡힌다.**

고치기 전 실측 — 같은 30분 체류인데:

| 표본 간격 | 5초 | 30초 | 120초 |
|---|---|---|---|
| 수정 전 | **20.9분** | 29.7분 | 30분 |
| 수정 후 | 29.6분 | 30분 | 30분 |

**정보가 가장 많을 때 결과가 가장 나빠지는 역전.** 같은 원인으로 GPS 정확도 60m인 30분
체류는 **아예 탐지에 실패**했다(지터 46m/5초 = 9.2 m/s → 차량으로 오분류 → 가중치 0.05).

→ 속도를 판정할 때만 변위에서 오차를 뺀다. **칠하는 위치는 실제 좌표 그대로다.**

### 6-2. 임계값 기준선의 가중치 (§4-4)

6-1을 고치면 촘촘히 표본된 걷기가 정지로 분류돼 만점 가중치(1.0)로 칠해진다. 그런데
임계값 기준선이 걷기 가중치(0.85)로 계산되어 있으면 통과 구간이 임계값을 넘어 샌다.
→ 기준선은 최대 가중치로 잡는다.

Kotlin 포팅 후 **같은 합성 궤적으로 같은 결과가 나오는지 확인할 것.** 참조 구현의 실측값
(지터가 난수라 ±소폭 변동):

| # | 시나리오 | 기대 결과 |
|---|---|---|
| 1 | 1.4 m/s로 700m 직진 통과 | **탐지 없음** |
| 2 | 한자리 30분 (지터 ±8m) | 1개, 체류 ≈29.7분, 반경 ≈28m, 확신 ≈0.89 |
| 3 | 반경 150m 안에서 40분 배회 | 1개, 체류 ≈34분, 반경 ≈42m, 확신 ≈0.90 |
| 4 | 15 m/s 차량 통과 + 신호대기 3분 | **탐지 없음** |
| 5 | A 25분 → B 25분 → A 재방문 25분 | **3개**, 각 ≈25분, A 두 개가 시간으로 분리 |
| 6 | 같은 30분 체류를 5/30/120초 간격으로 | 29.6 / 30 / 30분 — **간격과 무관하게 안정** |
| 7 | 30분 체류, GPS 정확도 60m | 1개, 체류 ≈27.9분, 반경 ≈110m, **확신 0.78로 낮게** |

1·4·8이 "탐지 없음"으로 나오는 것이 가장 중요하다 — 오탐이 미탐보다 나쁘다.
6은 6-1 결함의 회귀 테스트다.

## 8. 출력 → pplan 전송

핫스팟 하나가 `PathwalkTracePoint` 하나가 된다
(계약: `packages/shared/src/lib/pathwalk-import.ts`).

| 핫스팟 | → | `PathwalkTracePoint` |
|---|---|---|
| `lat`, `lng` | → | `lat`, `lng` |
| `startAt` | → | `timestamp` |
| `dwellMinutes` | → | `stayMinutes` |
| `confidence` | → | *(현재 계약에 자리 없음 — 아래 참조)* |
| `peakMinutes`, `radiusMeters` | → | *(현재 계약에 자리 없음)* |

**원시 위치 로그는 절대 서버로 보내지 않는다.** 이 알고리즘이 기기 안에서 전부 돌고,
찾아낸 거점만 나간다 — pplan 쪽도 같은 설계 제약을 문서화해 두고 있다
(`pathwalk-import.ts` 상단 주석).

### 계약 확장이 필요한 항목

`confidence`는 pplan의 후보 랭킹(`rankPlaceCandidates`)에 넣을 값으로 논의된
`trajectoryWeight`의 실체다. 현재 `PathwalkTracePoint`에 자리가 없으므로 **양쪽 합의 후
필드를 추가**해야 한다. `radiusMeters`도 넓은 장소의 POI 조회 반경을 정하는 데 쓸 수
있어 함께 보내면 좋다.

> 참고: 반경은 **임계값을 넘은 조밀한 핵심부**라 150m를 배회해도 42m로 보고된다(시나리오 3).
> 실제 활동 범위보다 보수적인 값이니 조회 반경으로 쓸 땐 여유를 두는 게 좋다.

## 9. Kotlin 포팅 메모

- 격자 키: 참조 구현은 `"cx:cy"` 문자열을 썼다(가독성 우선). Kotlin에선 `Long`
  패킹(`(cx.toLong() shl 32) or (cy.toLong() and 0xFFFFFFFF)`)이나 `data class` 키가
  낫다 — 음수 좌표를 다루므로 단순 곱셈 인코딩은 충돌 위험이 있다.
- 부동소수 누적: 하루치 궤적이면 `Double`로 충분하다(칸당 최대 수만 초 수준).
- 성능: 하루 17,000표본(5초 간격) × 칸 25개 ≈ 42만 회 갱신. 참조 구현 기준 수백 ms.
  실기기에서 부족하면 `paintGaussian`의 칸 수집 배열을 재사용 버퍼로 바꾸는 게 첫 최적화
  지점이다(알고리즘은 그대로).
- 세션 단위로 돌린다. `maxGapMinutes`가 이미 궤적을 끊으므로 하루치를 한 번에 넣어도
  되지만, 메모리를 아끼려면 세션별로 나눠 호출해도 결과는 같다.
